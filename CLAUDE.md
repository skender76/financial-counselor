# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal finance dashboard ("Dashboard Finanziaria"), **multi-user and hosted online** (VPS + Caddy for HTTPS; see README). UI text, code comments and log messages are all in **Italian**; keep new ones in Italian too. There is no build step, no package manager and no test suite. Git-tracked; `app.db` (every user's accounts, financial data and API keys) and the legacy `dati.json` / `ai-config.json` are gitignored and must never be committed.

## Files

- `financial-dashboard.html` — the whole dashboard (HTML + CSS + JS in one file), served by `server.py`. A first `<script>` ("// ===== Accesso") asks `GET /api/auth/me` synchronously: with no session (or when the URL fragment is `#verify=TOKEN` / `#reset=TOKEN`, from the emails — the token is read and stripped from the URL at once) it builds the auth screens with the `h()` DOM helper (login, 2FA code, register, forgot/reset password, email verification; never `innerHTML` with variable text) and sets `window.__authRequired`, which makes the main script throw at its first line (nothing else runs until the post-login reload). It also wraps `fetch` so every POST carries `X-CSRF-Token` (`window.__csrf`; one retry after a 403 via `window.__refreshSession()`, which refuses to continue if a *different* account logged in from another tab → `'other'`). The top bar has an "⚙️ Impostazioni" dropdown menu (`toggleSettingsMenu()`) holding Importa backup, Importa estratto conto, Esporta dati, Aggiorna dati, 🔑 Chiavi API (`openApiKeysModal()`, a modal wrapping `#apiKeysList`), 🧠 Memoria del consulente (`openMemoryModal()`, modal with the advisor memory note, editor and fixed rules), Sicurezza and the theme toggle; email, sync status and "Esci" stay in the bar. The "🔐 Sicurezza" item (`openSecurityModal()`) changes the password and enables/disables TOTP 2FA (secret + recovery codes shown once). The "⏻ Esci" button (`logoutDashboard()`) saves, then `POST /api/auth/logout`. The AI chat goes through `askAdvisor()` → `/api/ask`; `loadAdvisorInfo()` reads `/api/ai-info`. The `#fileSyncStatus` header indicator shows whether writes are reaching the server.
- `auth.py` — SQLite (`app.db`, mode 600, WAL) with tables `users`, `sessions`, `user_data` (the former `dati.json`, plus an integer `version` used as ETag `"v<N>"`), `user_ai_config` (the former `ai-config.json`) and `invites`; email verification and password reset via single-use hashed tokens in `email_tokens` (24 h / 1 h; accounts created while SMTP is configured start `verified=0` and cannot log in until confirmed; a duplicate registration returns the same 202 as a new one and mails the owner instead; forgot/resend answers are always identical and mails are capped per recipient by `_may_mail`; a reset closes every session but does **not** bypass 2FA); TOTP 2FA (RFC 6238, stdlib; `totp_last_step` blocks replay, login with 2FA returns an `mfa_token` valid 5 min / 5 attempts before any session exists, 8 single-use recovery codes stored hashed; disabling needs password + code); `encrypt_secret`/`decrypt_secret` (AES-256-GCM via `cryptography`, `DASHBOARD_MASTER_KEY`, `enc1:` prefix, bound to the row with a context like `ai:<user_id>` / `totp:<user_id>`; `server.py` refuses to start online without the key and migrates plaintext values with `encrypt_existing()`); passwords hashed with stdlib `hashlib.scrypt` (N=2^15, per-user salt, `compare_digest`, dummy hash for unknown emails so timing doesn't reveal accounts, NFKC-normalized, 12–256 chars); sessions store only the SHA-256 of the cookie token plus a CSRF token, idle 12 h / absolute 14 days; in-memory `Throttle` for failed logins (per account and per IP) and per-user limits. **Every data function takes the `user_id` from the session, never from request input** — keep it that way for any new endpoint. Registration mode `DASHBOARD_REGISTRATION` = `invite` (default, single-use codes) | `open` | `closed`. Security events go to stderr through `log_event()`. CLI: `python3 auth.py create-invite | import-legacy EMAIL | reset-password EMAIL | gen-master-key | encrypt-existing`.
- `mailer.py` — SMTP sender (`DASHBOARD_SMTP_HOST/PORT/USER/PASSWORD/FROM/SECURITY`; links use `DASHBOARD_PUBLIC_URL`). Sends from a background thread so response timing never reveals whether an address exists; failures only reach the log. `mailer.ENABLED` turns verification/reset on or off.
- `server.py` — Python 3 server (stdlib only apart from the AI SDKs), configured through env vars (`DASHBOARD_HOST` default 127.0.0.1, `DASHBOARD_PORT`, `DASHBOARD_PUBLIC_URL`, `DASHBOARD_TRUST_PROXY`, `DASHBOARD_REGISTRATION`, `DASHBOARD_DB`). Public: `GET /` and `/api/auth/{me,login,login-mfa,register,verify,resend,forgot,reset}`; everything else (`/api/data`, `/api/ask`, `/api/ai-info`, `/api/ai-keys`, `/api/import-statement`, `/api/auth/{logout,change-password,mfa/setup,mfa/enable,mfa/disable}`) goes through `_require_session()`, and POSTs also check the CSRF header. Each request must carry an allowed `Host` (the `DASHBOARD_PUBLIC_URL` netloc, or `localhost:PORT` / `127.0.0.1:PORT` when unset — blocks DNS rebinding); every POST must be `Content-Type: application/json` and any `Origin` must be an allowed host; bodies are size-capped per endpoint (`_read_json(max_bytes)`). Session cookie: `HttpOnly; SameSite=Strict`, plus `Secure` and the `__Host-` prefix when the public URL is https; security headers are added in `end_headers()`. CSP: JSON responses get `default-src 'none'`; the HTML page gets a per-response nonce injected into every `<script` tag by `_send_file()` (so an injected `<script>` does not run; Chart.js from jsdelivr keeps its SRI) — **any new `<script>` must be a literal `<script` in the HTML file so it receives the nonce**. `script-src-attr 'unsafe-inline'` and `style-src 'unsafe-inline'` remain on purpose because the page has ~110 inline `onclick=`/`onchange=` handlers and inline styles; removing them (event delegation) is what would allow a fully strict CSP. Optimistic concurrency on `/api/data`: GET returns an `ETag`, each POST sends it as `If-Match`; 409 if it changed (another tab), 428 if missing. Everything is `Cache-Control: no-store` on purpose. There is **no** shutdown endpoint any more (stop with SIGTERM/Ctrl+C; writes are SQLite transactions). `X-Forwarded-For` is trusted only from 127.0.0.1 and only with `DASHBOARD_TRUST_PROXY=1` (last value). The page is re-read from disk on every request but Python modules only at startup, so restart after changing Python code.
- `ai_providers.py` — vendor-neutral AI layer plus API-key management, **per user**: every public function takes `user_id` first (`list_keys`, `manage_keys`, `resolve`, `ask`, `info`) and keys live in `user_ai_config` as `{active_key_id, keys: [{id, name, provider, value, model, expires, notes, created}]}` — deliberately **not** in the user's data blob, so keys never reach exports/backups. **Never return a key's `value` to the page** (`_public_key()` exposes only the last 4 chars); on `update` an empty value means "keep". Keys are encrypted at rest by `auth.write_ai_config()`/`read_ai_config()` (callers here always see plaintext). `ask()` uses only the active key, refuses it if `expires` is in the past, and falls back to the provider's `default_model` (only Anthropic has one) when `model` is empty. No env-var fallback. Vendors: `anthropic`, `openai`, `gemini` (own SDKs) and `mistral`, `deepseek`, `xai`, `openrouter` (`OpenAICompatibleProvider`: the `openai` SDK with the vendor's `base_url` and chat completions — adding another OpenAI-compatible vendor is a 5-line subclass). Only Anthropic has a `default_model`; never guess model names for the others. `AnthropicProvider.request_options()` sends adaptive thinking / `effort` / server-side `fallbacks` only to models listed (by ID prefix) in `ADAPTIVE_THINKING_MODELS` / `EFFORT_MODELS` / `FALLBACK_MODELS` — e.g. `claude-haiku-4-5` gets a plain request; extend these tables when adding models. If a 400 still says an option is "not supported", it retries once without them. Show vendors' error text via `api_error_message()`, not the raw exception dump. Each provider lazy-imports its SDK. Some vendors report a bad key as 400 (Gemini `API_KEY_INVALID`, xAI "Incorrect API key"): map those to the "chiave non valida" message. Adapters must translate every vendor error into `AdvisorError(message_in_italian, http_status)`. To add a vendor: subclass `Provider`, implement `import_sdk`/`make_client`/`ask`, register it in `PROVIDERS`, and add its key prefix to `detectApiKeyProvider()` in the page.
- `statement_import.py` — reads bank statements for the "📑 Importa estratto conto" item of the Impostazioni menu (`POST /api/import-statement` `{account, kind, filename, content_b64, since?}` → `{movements, ignored, summary}`; the file travels base64-encoded inside JSON to satisfy the JSON-only POST rule). `parse_statement()` dispatches by account: Revolut `.csv`, BPER `.xls` (needs `xlrd`), Fineco `.xlsx` (needs `openpyxl`, lazy-imported); `kind` `carta` (credit-card report) exists only for BPER. It only normalizes — each movement is `{date, direction, account, movement, amount>0, description, details, tag, provisional, source_kind}` with `movement` using the Movimenti register's values and `tag` a hint (`stipendio`, `mutuo`, `possibile_giroconto`, `spese_bancarie`, `imposte`, `investimento`). Only movements from `IMPORT_START_DATE` (2026-01-01) are returned; Revolut currency exchanges (`cambio_valuta`) and BPER account card settlements (`regolamento_carta`) are not expenses and go to `ignored` instead (the settlement lines of the card report are dropped, otherwise card spending is counted twice). BPER files are cross-checked against their own row count and Totale row. No bank file carries a stable transaction ID, so matching relies on account+direction+amount+date.
  The page side (`// ===== Importazione estratti conto` in `financial-dashboard.html`) does the rest, nothing is written until the review screen is confirmed: the file is the source of truth for its window — a registered movement with the same account/direction/amount and date ±3 days is **replaced** (keeps its `id`, its manual category unless it is `Varie`/`Altro`/`Altro reddito`, and `autoMortgage`, otherwise `applyRecurringMortgage()` would regenerate the instalment), unmatched file rows are added, registered movements missing from the file are **flagged** (default "Mantieni", never auto-deleted). Imported entries carry `imported`, `source`, `noBalance: true` (account balances never change on import, so `deleteExpense`/`deleteTransfer` skip the balance reversal for them) and, for card purchases, `ccApplied: true`. Own-account transfers are paired across accounts (equal amount, opposite direction, ±3 days, at least one leg a `possibile_giroconto`/`transferHint`) and become an entry in `skender_fin_transfers_v1` replacing both legs; a leg already covered by a registered transfer is not imported. Categories: deterministic by tag → learned rules (`skender_fin_category_rules_v1`, learned only from categories the user set or already had, never from unreviewed AI output) → AI via `askAdvisor` (batches of 40, descriptions masked by `maskForAi`: IBANs, long numbers and names after "a favore di"/"Beneficiario" removed; no dates or account names are sent). `Varie` is never suggested because it requires a `necessity`.
- `avvia-dashboard.command` — double-clickable macOS launcher; runs `server.py` with `.venv/bin/python` when `.venv` exists.

## Running

```bash
python3 -m venv .venv && .venv/bin/python -m pip install anthropic   # once; for the AI chat install the chosen vendor's SDK (anthropic | openai | google-genai); for statement import also `xlrd openpyxl` — Homebrew Python blocks global pip
.venv/bin/python server.py   # serves the dashboard on localhost:8765, stores everything in ./app.db (avvia-dashboard.command does this); first user: `python3 auth.py create-invite`, then register in the page
```

## Architecture (single-file vanilla JS + Chart.js from CDN)

- **All of a user's state lives in their `user_data` row (the JSON blob formerly called `dati.json`), under keys prefixed `skender_fin`** (e.g. `skender_fin_v5` main data, `_accounts_v1` (Liquidità accounts `{id, name, bank, note, balance}`: `name` is the key movements/transfers/flows/mortgage use, so renaming goes through `renameAccountEverywhere()`; `bank` = `Fineco|BPER|Revolut|''` ties an account to the statement importer and the BPER card due rule, so those work only for the three original accounts even if renamed; deleting an account in use is blocked; balances change only via `adjustAccountBalance()`, and `captureUndo()` snapshots this key), `_investments_v1`, `_properties_v1`, `_expenses_v1`, `_transfers_v1`, `_category_rules_v1`, `_flows_v1`, `_chat_v1`, `_memory_v1`, `_theme`, `_last_modified_v1`). Each domain has `load*/save*` helpers and a `migrateLegacy*` function that lifts older fields out of the main `skender_fin_v5` object. Bump/migrate rather than silently changing the shape of stored data.
- **The server-side blob is the single source of truth — never use `localStorage`/`sessionStorage`/IndexedDB for data (not even UI prefs).** The page reads/writes only through `store` (top of the main `<script>`): `store.load()` does a *synchronous* GET at startup (if it fails the page shows "Dashboard non disponibile" and stops — no offline fallback), and every `store.setItem()` synchronously POSTs the **whole** state, so when it returns the data is on disk. Optimistic concurrency: GET returns an `ETag` (the row's version number), each POST sends it as `If-Match`; the server answers 409 if the data changed meanwhile (another tab) and 428 if `If-Match` is missing (a tab running an old version) — on 409 the page stops writing and asks for a reload; on network failure it alerts once and retries every 5 s, and `beforeunload` warns while something is unsaved. `migrateLegacyBrowserStorage()` is a one-time cleanup of the copy older versions kept in `localStorage` (imported into `dati.json` only if newer and the user confirms).
- `touchLastModified()` sets `LAST_MODIFIED_KEY`; call it from every data-mutating operation. That timestamp is distinct from `d.lastUpdated` (only set by the "Aggiorna dati" modal). CSV backup import compares against it: a backup not newer than current data can still be imported, but only after two explicit `confirm()` dialogs (summary with warning + definitive confirmation).
- **Startup automation** (bottom of the script): `migratePendingCcDueMonths()`, `applyMaturedCreditCardCharges()` (deferred credit-card charges hit the account balance on the due date) and `applyRecurringMortgage()` run on every load, then all `render*()` functions.
- **Net worth math** is in `render(d)`: liquid net worth deliberately excludes pension/TFR (Fondo Cometa) and properties.
- **Movimenti — inserimento e modifica** (`// ===== Inserimento e modifica movimenti` in the page): the "+ Aggiungi movimentazione" modal is a table of rows with one shared account; the ✏️ button in the table reopens the same modal for one entry (`openExpenseModal(id)`). Saving is a single pass (`saveExpenseBatch`): one `adjustAccountBalance` per account, then one `saveExpenses`. Balance effects always go through `balanceEffect(entry)` (same rule as `deleteExpense`: `noBalance` → 0, deferred credit-card charge → 0 until `ccApplied`); an edit reverts the old effect and applies the new one, and `buildBatchEntry` keeps unknown fields (`imported`, `source`, `autoMortgage`, `noBalance`) and recomputes `ccDueMonth`/`ccApplied`. Errors block only their row; warnings (future/old date, possible duplicate ±3 days) need a second "Salva". Last-used account/direction/type live in `skender_fin_entry_defaults_v1`. `suggestCategory()` proposes a category from the learned rules (`skender_fin_category_rules_v1`, same `categoryRuleKey` as the statement import) or the most used one for that description, never `Varie`; `learnCategoryRules()` feeds those rules from saved rows. "📋 Incolla righe" turns pasted `data; descrizione; importo` lines into rows via `parsePastedRows()` (unparsable fields stay empty so the error shows in review). Save and delete take a `captureUndo()` snapshot (balances + movements) and show a 10 s "Annulla" toast (`offerUndo`/`undoLast`); undo refuses if `LAST_MODIFIED_KEY` changed meanwhile, so any new operation that should be undoable must call `touchLastModified()` before `offerUndo`. The table rows have ⧉ (`duplicateExpense`: opens the insert modal prefilled, date today) and a checkbox column driving `renderExpenseBulkBar`/`applyBulkEdit` (change category and/or account of the selection, never to `Varie`; it reuses `buildBatchEntry` + `balanceEffect` so account changes move balances and credit-card due months correctly, and is undoable). Any new entry field must be handled in `buildBatchEntry` and, if it affects balances, in `balanceEffect`.
- **Export/import**: CSV report and a versioned CSV backup (`BACKUP_FORMAT_MARKER`/`BACKUP_FORMAT_VERSION`), plus a recovery path for movements (`processRecoveredMovements`).
- **AI advisor chat**: two-pass flow in `sendChat()` — first prompt asks the model for a JSON calculation plan (`buildCalcPlanPrompt` → `parseCalcPlan`), expressions are evaluated locally by a small recursive-descent parser (`safeEval`, no `eval`), then a final prompt (`buildFinalPrompt`) includes the verified results plus `formatFinancialSnapshot(d)`. This exists to avoid LLM arithmetic errors — don't let the model compute numbers directly. A user-editable "memory" block is also fed into prompts. Market/tax context is a hardcoded snapshot, not a live feed.
- Theming uses CSS variables on `:root` with a `[data-theme="dark"]` override; charts are updated via `updateChartDefaultsForTheme()`.
